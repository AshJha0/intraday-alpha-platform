# tests/ — the six-level testing strategy

Everything that keeps four independent implementations of one pinned
semantics identical (spec §21, PLATFORM_CONVENTIONS.md §5/§9). Every level
below is run by CI (`.github/workflows/ci.yml`); the single local equivalent
is `bash tests/harness/run_all.sh`, which prints the parity table in README.

| Level | Where it lives | What it proves | Exact command (from the repo root) |
|---|---|---|---|
| 1. **Unit** (per language) | `python/tests/`, `cpp/tests/`, `rust/*/tests/` + `#[cfg(test)]`, `java/src/test/` | each component's contract in isolation: codec domain rules, book semantics, feature families, alphas, risk rules, execution simulator, SOR, platform wiring. Property-style tests (random event streams vs the brute-force book, invariants under fuzzed input) live INSIDE these suites next to the code they exercise. | `cd python && PYTHONPATH=src python3 -m pytest -q`<br>`cd cpp && bash build.sh && ctest --test-dir build --output-on-failure`<br>`cd rust && cargo test --workspace`<br>`cd java && bash build.sh && bash test.sh` |
| 2. **Golden** (cross-language) | `tests/golden/` (vectors + expected outputs, generated by the Python reference) and each language's golden group | all four languages produce the same bytes / integers / 1e-9 floats for the same pinned inputs: IAP1 SHA-256, book states, checkpoints, anomaly counters, features, alphas, risk decisions + audit, fills, portfolio, TCA, adaptive | `bash tests/harness/run_golden.sh` (= `run_all.sh --golden-only`) |
| 3. **Replay** (determinism) | `tests/replay/` | same seed ⇒ identical bytes: a seeded generator or pipeline stage re-run reproduces its output byte-for-byte (`tests/replay/README.md`) | `python3 -m pytest -q tests/replay` |
| 4. **Integration** (cross-component) | `tests/integration/` | end-to-end chains wired the way the platform wires them (decode → book → features → …) over a real vector, asserting the contract at the end of the chain (`tests/integration/README.md`) | `python3 -m pytest -q tests/integration` |
| 5. **Research validation** | `python/src/iap/validation/` (metrics, stress, statistical gates) exercised by `python/tests/test_validation_framework.py`, `test_model_gate.py` and the research scripts under `research/*/run_*.py` | research claims are honest: purged/embargoed CV, IC with proper tolerances, capacity bounds from reference data, stress multipliers, the ML promotion gate; the headline numbers in README are re-derived from the artefacts by `tests/harness/check_headline_numbers.py` | `cd python && PYTHONPATH=src python3 -m pytest -q -k "validation or model_gate"`<br>`python3 tests/harness/check_headline_numbers.py` |
| 6. **Deployment** | `tests/harness/check_deployment.py` (+ `check_docker_build.py`) | the deployment artefacts are structurally valid and consistent with the code: promtool rules/config/unit tests, compose, Dockerfile COPY sources against a clean checkout, k8s manifests + singleton shape, ConfigMap sync AND the ConfigMap `items[]` that project the nested `configs/<domain>/` tree, dashboard metric provenance, Java golden-gate completeness | `python3 tests/harness/check_deployment.py --verbose` |

Levels 3 and 4 need no `PYTHONPATH`: `tests/conftest.py` inserts
`python/src` into `sys.path`, so `python3 -m pytest -q tests/integration
tests/replay` works from the repository root. They are the `integration`
and `replay` rows of the parity table and count toward its verdict.

## Layout

```
tests/
  README.md            this file
  conftest.py          sys.path shim for the repo-level pytest suites
  golden/              cross-language golden vectors + expected outputs (level 2)
  harness/             run_all.sh, run_golden.sh, check_deployment.py,
                       check_docker_build.py, check_headline_numbers.py
  integration/         level 4 (README.md + tests)
  replay/              level 3 (README.md + tests)
```

Rules that apply to every level (PLATFORM_CONVENTIONS.md §5, §9):

- A golden file is regenerated ONLY by the Python reference tool under
  `python/tools/make_golden_*.py`, validated first against an independent
  brute-force implementation, and the change is recorded in
  `schemas/MIGRATIONS.md`.
- Counts printed by the harness are truthful: `-` means "did not run in this
  mode", `?` means "ran but unparseable", and both fail the run. A test is
  never deleted or skipped to get green.
- Each language's full run stays under 120 s; the repo-level suites stay
  well under a minute.
